1) Phase2 목표 정의 (완료 기준 DoD)
Phase2 목표: “케이스 1건”을 대상으로 사용자가 아래를 끝까지 수행하면, 시스템이 AI 분석→권고→(시뮬레이션/승인/실행) 흐름을 보여주고, 모든 단계가 감사로그로 추적 가능해야 함.
DoD(필수):
A. 케이스 상세 AI 탭이 ‘빈 화면’이 아니라, BE가 제공하는 분석결과/추론(reasonText)/근거(evidence)/점수(score)/confidence breakdown을 표시
B. ‘분석 시작’ 버튼이 Aura 분석 트리거를 실제로 발생시키고, 진행상태가 Stream으로 표시(최소: STARTED→RUNNING→COMPLETED/FAILED)
C. 유사 케이스 탭이 최소 N개(예: 0~3개) 검색 결과를 표시하고, 선택 시 비교/링크 제공
D. RAG 탭이 “근거 문서 리스트(정책/규정/내부 가이드)”를 표시하고, 각 근거에 출처/스니펫/신뢰도 등 최소 메타 포함
E. 우측 “액션” 영역에서 “권고 조치(Action Proposal)”가 목록으로 생성되어 노출(Phase2에서는 ‘실행’까지 강제하지 않아도 됨 — 승인/거절/보류 상태 흐름까지만)
F. 위 A~E의 주요 상태 변화/승인/거절/실행/실패가 audit_event_log에 일관된 스키마로 기록(누락/NULL 최소화)

2) 앞으로 남은 단계(권장 로드맵)
- Phase1: E2E 기반/감사/코드/필터/상태 변경 확인  ✅ (완료로 판단)
- Phase2: Agentic AI “분석+근거+스트림+권고” 구현 (이번 단계)
- Phase3: 자율조치/가드레일/승인 워크플로우 고도화 + 실제 외부 연동(지급차단/역분개 등) ‘시뮬레이션→승인→실행’ 완결
- Phase4: 운영화(스케줄/재시도/관측성/권한/RBAC/멀티테넌시) + 품질(성능/부하/데이터규모) + 보안(PII 마스킹/감사 무결성)
⇒ “향후 남은 단계”는 Phase2 포함하여 총 3단계(Phase2~4)가 남았다고 보면 됨.

[프롬프트 #1] BACKEND (Phase2) — Aura 연동 + 분석 결과/스트림/유사/RAG/액션 제안 API 설계/구현
대상: dwp-backend (SynapseX 모듈)
목표: 프론트가 탭 5개를 실제 데이터로 채울 수 있도록 API를 확정/구현하고, Aura 플랫폼과의 호출/콜백/저장 구조를 만든다.

1) 핵심 개념(Phase2에서 추가/확정해야 할 도메인)
- CaseAnalysisRun: 케이스 분석 실행 단위 (caseId, runId, status, startedAt, finishedAt, model, params, error)
- CaseAnalysisResult: 분석 결과(요약/점수/근거/신뢰도/유사케이스/RAG refs)
- CaseActionProposal: AI가 “권고한 조치” (type, riskLevel, rationale, requiredApproval, simulationOnly, payload)
- Audit: 위 엔티티 변경 시 audit_event_log 남김

2) API 계약(권장) — 최소 세트
(1) 분석 트리거
POST /api/synapse/cases/{caseId}/analysis-runs
- request: { mode: "LIVE"|"SIMULATION", requestedBy: "HUMAN"|"SYSTEM", options?: { topKSimilar?: number, ragTopK?: number } }
- response: { runId, status:"STARTED", streamUrl:"/api/synapse/analysis-runs/{runId}/stream" }

(2) 분석 실행 상태 조회
GET /api/synapse/analysis-runs/{runId}
- response: { runId, caseId, status, progress?, startedAt, finishedAt, error? }

(3) 분석 스트림 (SSE 권장)
GET /api/synapse/analysis-runs/{runId}/stream   (Content-Type: text/event-stream)
- event types: started | token | step | evidence | confidence | similar | rag | proposal | completed | failed
- 최소: started/completed/failed + step 2~3개라도 표시

(4) 케이스 분석 결과 조회(캐시된 결과)
GET /api/synapse/cases/{caseId}/analysis
- response: { score, severity, reasonText, confidenceBreakdown, evidence[], similarCases[], ragRefs[], proposals[] }
- NOTE: 기존 /api/synapse/cases/{id} 응답의 reasoning/evidence/action 필드와 “중복/충돌”이 없도록 정리 필요:
  - 권장: case detail은 “스냅샷” 최소만 두고, 탭 데이터는 별도 endpoint로 분리(Phase2)

(5) 액션 제안 목록(케이스 기준)
GET /api/synapse/cases/{caseId}/action-proposals
POST /api/synapse/cases/{caseId}/action-proposals/{proposalId}/approve
POST /api/synapse/cases/{caseId}/action-proposals/{proposalId}/reject
POST /api/synapse/cases/{caseId}/action-proposals/{proposalId}/execute (Phase3에서 실연동, Phase2는 simulation flag만)

(6) 유사 케이스 단독 조회(옵션)
GET /api/synapse/cases/{caseId}/similar?topK=3

(7) RAG 근거 단독 조회(옵션)
GET /api/synapse/cases/{caseId}/rag?topK=5

3) DB 스키마(Phase2 최소)
- synapse_case_analysis_run
  - run_id (PK, uuid), case_id (FK), status, mode, requested_by, started_at, finished_at, error_message, aura_trace_id, created_at
- synapse_case_analysis_result
  - run_id (PK/FK), score, severity, reason_text, confidence_json, evidence_json, similar_json, rag_refs_json, created_at
- synapse_case_action_proposal
  - proposal_id (PK, uuid), case_id, run_id, type, status(DRAFT|PROPOSED|APPROVED|REJECTED|EXECUTED|FAILED), risk_level, rationale, payload_json, created_at, updated_at
※ JSON 컬럼은 Postgres jsonb 권장

4) Aura 연동 방식(Phase2 권장: “요청→비동기 결과 저장”)
- BE → Aura: POST /aura/cases/{caseId}/analyze (or /runs) 로 분석 요청
- Aura → BE: (A) 콜백 POST /api/synapse/internal/aura/callback (권장) 또는 (B) BE 폴링
- Phase2에서는 운영 단순화를 위해 “콜백 1개”로 통일 권장
- 콜백 payload에는:
  - runId, status, partialEvents(optional), finalResult { score, reasonText, confidence, evidence, ragRefs, similar, proposals }

5) 감사로그(audit_event_log) 규칙(Phase2 확대)
- ANALYSIS_RUN_STARTED / ANALYSIS_RUN_COMPLETED / ANALYSIS_RUN_FAILED
- ACTION_PROPOSED / ACTION_APPROVED / ACTION_REJECTED / ACTION_EXECUTED(Phase3)
- 각 이벤트의 after_json은 반드시 채우고, diff_json은 가능하면 채우되 Phase2에서는 after_json 우선
- actor_type: SYSTEM(Aura/Batch) vs HUMAN(사용자)
- resource_type/resource_id: CASE / {caseId}, ANALYSIS_RUN / {runId}, ACTION_PROPOSAL / {proposalId}
- trace_id/aura_trace_id 연계 (관측성)

6) BE 구현 체크리스트(완료 기준)
- Postman으로: trigger → stream 연결(최소 started/completed 이벤트) → analysis 조회 결과가 non-empty
- caseId 하나로: proposals 최소 1개 생성되어 action-proposals API에서 반환
- audit_event_log에 3종 이벤트 이상(STARTED/COMPLETED/PROPOSED) 남는지 확인
- DEMO_OFF에서도 “빈 데이터 fallback”이 깨지지 않도록 null-safe
