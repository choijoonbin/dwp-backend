[SynapseX][Phase A] 감사추적로그 필터 코드화 + 케이스 단위 감사조회(선택) + 상태변경 Audit 정책 정리 (Backend Prompt)

목표
- Audit 화면에서 사용하는 필터 옵션을 ‘코드 테이블’ 기반으로 제공하여 프론트 하드코딩을 제거한다.
- Phase A 범위에서 “상태 변경 → audit_event_log 기록” 흐름이 명확하고 일관되게 남도록 정책을 고정한다.
- (선택) 케이스 상세의 ‘감사 스트림’ 탭이 단순 링크가 아니라 케이스 단위 최근 이벤트 타임라인을 표시할 수 있도록 API를 제공한다.
- Phase B(조치 추천/생성/실행)는 이번 범위가 아니므로, actions 목록이 0건이어도 정상임을 전제로 한다.

================================================================================
1) Audit Filter용 코드 그룹 설계/시드
================================================================================

1-1. 요구 코드 그룹(필수)
- groupKey:
  - AUDIT_CATEGORY
  - AUDIT_EVENT_TYPE
  - AUDIT_OUTCOME
  - AUDIT_ACTOR_TYPE
- (선택) AUDIT_SEVERITY, RESOURCE_TYPE

1-2. 제공 방식
- 기존 Admin codes API를 그대로 사용:
  - GET /api/admin/codes?groupKey=AUDIT_CATEGORY
- 코드 테이블 스키마/엔티티는 기존 sys_code(또는 sys_codes) 사용
- sortOrder로 FE 정렬 가능하도록 입력

1-3. 시드 데이터(원칙)
- “코드가 존재하지만 시스템에서 안 쓰는 값”을 과도하게 넣지 말고,
  현재 audit_event_log에 실제로 적재되는 이벤트 타입 중심으로 1차 구성한다.
- 예:
  - AUDIT_CATEGORY: CASE, DOCUMENT, OPEN_ITEM, ACTION, SYSTEM, AUTH, ADMIN ...
  - AUDIT_OUTCOME: SUCCESS, FAILURE
  - AUDIT_ACTOR_TYPE: HUMAN, AGENT, SYSTEM
  - AUDIT_SEVERITY: INFO, WARN, ERROR, CRITICAL
  - AUDIT_EVENT_TYPE: CASE_VIEW_LIST, CASE_VIEW_DETAIL, STATUS_CHANGE, CASE_ASSIGN, CASE_COMMENT_CREATE, RUN_DETECT_* 등

1-4. DoD
- FE는 하드코딩 없이 코드 API로 옵션을 받아 렌더링 가능
- isActive/tenantId(null=global) 정책 유지

================================================================================
2) Audit 조회 API의 필터 파라미터 정리(기존 유지 + 가이드)
================================================================================

2-1. 기존 Audit 조회 API 확인
- 현재 감사추적로그 화면이 호출하는 API를 확인(예: /api/synapse/audit-events 등)
- 필터 파라미터가 없거나 부족하면 최소한 아래를 지원:
  - timeRange/from/to (미지정 시 기본 24시간 정책이면 문서로 명시)
  - category
  - eventType
  - outcome
  - actorType
  - q(검색어): caseId/resourceId/actorDisplayName 등을 하나의 q로 검색 가능하게

2-2. (선택) 케이스 단위 타임라인 API
- FE ‘감사 스트림’ 탭에서 바로 쓰기 위한 경량 API
  - GET /api/synapse/audit-events?caseId={id}&page=0&size=20
  - 또는 GET /api/synapse/cases/{id}/audit-events
- 최소 컬럼만 반환:
  - auditId, createdAt, eventCategory, eventType, outcome, severity,
    actorType, actorDisplayName, resourceType, resourceId, summary(optional)

================================================================================
3) 상태 변경 Audit 정책(Phase A 고정)
================================================================================

3-1. 상태 변경 이벤트 기록(필수)
- 케이스 상태 변경 API에서 audit_event_log 1건을 남김
  - event_type: STATUS_CHANGE
  - resource_type: CASE
  - resource_id: caseId
  - outcome: SUCCESS/FAILURE
  - severity: INFO
- before_json/after_json/diff_json:
  - STATUS_CHANGE는 before/after/diff 모두 채우는 것을 표준으로 고정
  - diff_json은 status 변경만 포함해도 됨

3-2. ‘액션 승인/거절/정보요청’ 의미(Phase A)
- Phase A에서는 조치(action record) 생성/실행이 아니라 “케이스 상태 변경 + 감사 기록”까지만 보장
- 각 버튼이 호출하는 엔드포인트의 상태 매핑을 주석/문서로 고정:
  - 해결 처리 -> RESOLVED
  - 무시 처리 -> DISMISSED
  - 정보요청 -> (정책 결정) TRIAGED 또는 IN_PROGRESS 유지 등

================================================================================
4) Codes / I18N 고려(간단)
================================================================================
- codes API는 Accept-Language에 따라 label/name_ko/name_en을 반환하는 현재 방식을 유지
- AUDIT_* 코드도 동일하게 다국어 컬럼(ko/en)로 시드 구성 가능
